# Host operations cross-module certification

PR472 adds the Host device registry to the existing native incident/reply package. Its additive schema change triggers sales and Airbnb workflows whose scope gates were written for earlier, narrower projects. At a9557b8 those gates failed before their runtime tests ran; the Host foundation suite itself passed.

The six workflows now recognize this exact PR/repository/branch/base combination through scripts/verify-host-mobile-operations-scope.mjs. The verifier requires the complete explicit file list, the pinned base 69434d924208153a444ef5716e7c414380dff899 and its ancestry. Candidate file scope is measured at the event head SHA, not at GitHub's synthetic merge commit, so unrelated main-branch files are not attributed to Host. The checkout must include that candidate and have its exact schema; whitespace checks cover both candidate and checkout. Removing the exact three Host models and user relation block must restore the entire base schema byte for byte. Sales/OTA runtime implementation files are not allowed. The only sales test-file exception moves the existing expiry-drain fixture from a one-second-old call (exactly on an exclusive window boundary in a fast run) to ten seconds old, clearly inside the 20-to-1-second-old expired window. The scope verifier requires that exact one-line replacement and preserves every assertion and all other test content. The call remains younger than the 60-second duration limit, so the test still proves window expiry rather than duration expiry. A changed base or additional scope requires fresh review; the verifier fails closed.

Only the obsolete project-specific scope gate gains a Host branch. All later sales/Airbnb type checks, database suites, fingerprint checks, transport tests and bundle steps remain. For the two migration certifications, disposable databases start from the unchanged base schema and apply the actual Host registry migration, then check full schema parity and the retained sales sentinel/contracts. They do not replay already-integrated sales migrations.

The verifier's negative tests cover wrong PR/fork/branch/base, extra and missing files, altered existing sales/OTA/user schema, changed Host models and duplicate/missing relations. These checks supplement rather than replace runtime certification. A successful scope check alone is not integration or release approval.

The disabled delivery candidate extends the same registry migration with a metadata-only HostMobilePushDelivery ledger and a monotonic device binding version. The exact Host-model suffix and explicit file allowlist are updated to that reviewed candidate; every pre-existing schema definition still restores byte for byte. The existing foundation workflow additionally runs the delivery unit/PostgreSQL tests, strict types and emitted build. Its AuthSession test prerequisite comes from the exact existing canonical CREATE statement and is applied only inside the isolated Host test database. Sales/OTA runtime checks and migration parity checks remain unchanged.

No production database, flag, provider, guest message, store build or deployment is changed. Companion Host PR7 contains preferences and native permission/token/tap handling; its exact-head runs passed. The disabled delivery implementation and its remaining integration/physical gates are documented in docs/host-mobile-push-delivery.md.
