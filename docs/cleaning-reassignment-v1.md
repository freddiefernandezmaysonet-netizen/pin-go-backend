# Cleaning cancellation and sequential backups — block 4

Applies to every current/new property through the existing staff configuration. No canary restriction, new infrastructure, schema migration, push, merge or deployment in this block.

Confirmed cleaner tasks expose an explicit two-step cancellation in My cleanings and the existing token portal. Cancellation is allowed before recorded start, including before timing consent. The authenticated API resolves Staff from the session; bearer-token actions use the assigned Staff and revalidate active same-organization PropertyStaff. Start and cancellation share the reservation lock; cancellation after recorded start/completion is rejected. Repeated withdrawal does not create another offer.

Withdrawal closes the offer (`CANCELLED`, `DECLINED`, or `EXPIRED`) and any unstarted work, preserving history. It selects an active principal/backup in configured order, excluding earlier attempts, missing phone/duration configuration and incompatible work. It respects the real next occupancy deadline, including previously applied early check-in. The same checklist stays attached to the departure reservation. No NFC/grant/StaffAssignment changes are made by this service.

Availability acceptance serializes per Staff and reservation. It rechecks offer status, other current offers/work, remaining time and conflicting cleaner commitments. The 120-minute response limit from the existing sent SMS is also rechecked at submission rather than waiting for the worker. The accepted assignment snapshots that cleaner's configured duration/grace values, but does not record timing consent or work start. Existing explicit timing consent/start remain required. A replacement can accept after the original scheduled start only if sufficient permitted time remains; its record retains the canonical scheduled start and no backdated declaration is created.

Both the existing pending-offer decline route and timeout processor now use the same transactional withdrawal service. Booking ingest replay preserves the existing offer history instead of reopening the cancelled principal or competing with an active replacement. Timeout/decline replays do not create duplicate backups. The existing notification worker sends the same offer family using Staff language; no message was added or sent during these tests.

A replacement with missing/invalid duration or a conflict is skipped. Acceptance refuses stale or ambiguous assignments rather than guessing. If no viable backup remains, cancellation and canonical Mission Control attention now commit together; see `cleaning-backup-exhaustion-v1.md`. Pin AI recovery remains pending, so exhaustion is not yet a fully autonomous recovery flow.

Existing stay-time departure validation binds to the current confirmed, consented work and duration; cancelled work is excluded and pending replacement offers cannot authorize new proposals. Already applied guest arrival times cap the replacement schedule. This block does not change/refund previously approved stay-time operations or implement new Pin AI proposal recalculation.

Current compatibility: acceptance requires configured cleaner/property duration (15–1440 minutes) and valid grace values. Missing configuration is shown as an unavailable schedule instead of confirming a task without its work commitment. Phone provisioning/delivery and shared-grant behavior require release testing; local SQL tests intentionally perform no provider calls.

Validation: disposable embedded PostgreSQL tests exercise ownership, acceptance/idempotency, cancellation, slow-backup skip, unchanged checklist/NFC identity, stale duration, sent-offer response expiry, conflicting work/duplicate offers, replacement start, cancellation rejection after start and exhausted decline. React runtime validates the two-step cancel and refreshed status. Relevant account/action/stay-time/SMS/language regressions, mobile HTML responses, TypeScript, lint, frontend build and backend bundle pass. PGlite does not certify native concurrent PostgreSQL sessions. Full phone/SMS/NFC evidence remains pending an authorized deployment.
