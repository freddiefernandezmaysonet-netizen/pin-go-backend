# Apple App Review account — staged, not activated

This change prepares an isolated Host reviewer account. It does not provision
production data, activate an exception, deploy code, create a Guest reservation,
connect a lock, or submit either app to Apple.

## Provisioning

Run from the backend deployment environment using its normal database access.
Set `PINGO_APP_REVIEW_OPERATOR_USER_ID` to the existing active PLATFORM_ADMIN's ID.
This is an operator script, not a public endpoint or a Dashboard signup workflow.

```sh
node --import tsx src/scripts/provision-app-review-account.ts
```

The default is a read-only plan. After checking the operator and plan, use:

```sh
node --import tsx src/scripts/provision-app-review-account.ts --apply
```

The transaction creates only `Pin&Go App Review` (`pin-go-app-review`) and
`apple-review@pin-ngo.com` with ORG_ADMIN permissions in that new organization.
Existing emails or slugs cause a stop; nothing is repurposed, reset or deleted.
No subscription, payment, reservation, property, provider connection or email is
created. The output contains IDs and the operator ID, never a password.
An unknown random bootstrap password is hashed. The alias owner must use the
existing Forgot Password flow to set a password, then enter it securely in App
Store Connect. This script does not trigger that email or store the new password.

## Temporary MFA exception

Disabled by default. Configure only after provisioning and verification:

- `PINGO_APP_REVIEW_ENABLED=true`
- `PINGO_APP_REVIEW_USER_ID`: exact new user ID from the script
- `PINGO_APP_REVIEW_ORGANIZATION_ID`: exact new organization ID from the script
- `PINGO_APP_REVIEW_EXPIRES_AT`: UTC ISO timestamp with milliseconds, for example
  the form `YYYY-MM-DDTHH:mm:ss.sssZ`; must be in the future and within 30 days
- Existing `PINGO_SESSION_MODE` must already be `ENFORCE`. Do not change a global
  security mode merely to activate this feature; audit it separately if needed.

The account must still pass the normal password and active-account checks.
Both IDs, the fixed email, role, organization slug and deadline must match.
The organization must have no other user, no lock, no TTLock authentication,
no PMS connection, no subscription, no Stripe customer/Connect account and no
public booking enabled. Scope violations fail login, rather than silently
creating an exempt session. Missing, disabled, invalid or expired configuration
uses the normal MFA path. Global MFA configuration remains unchanged, including
its existing configuration-error protection.

An exempt login creates a transactionally audited, nonrolling session, capped at
the earlier of 24 hours or the exception deadline. No trusted-device token is
minted. The account can log in again during the approved exception period.
Disabling the exception stops new exempt logins; it does not revoke sessions
already issued. To terminate all reviewer access, disable the reviewer user and
increment its tokenVersion through the normal controlled administration process.

## Validation and remaining gates

```sh
node --import tsx --test src/auth/app-review-access.test.ts src/auth/app-review-login.test.ts src/services/provision-app-review-account.test.ts src/auth/enterprise-auth-e8b.test.ts src/auth/host-session.policy.test.ts src/auth/host-session-token.test.ts
npx tsc -p tsconfig.app-review.json
```

57 selected tests pass. New code passes the scoped TypeScript check. The actual
Express login handler is exercised with synthetic persistence, password, token
and email boundaries (no production credentials or network calls). Its review
policy and session creation code are real. PostgreSQL transaction behavior and
production end-to-end login have NOT been certified by these tests.

The auth route bundles with esbuild and its generated JavaScript passes
`node --check`. The global `tsc --noEmit` baseline exhausts the default Node heap
before any change. An additional E7 suite has one pre-existing failure: its
registration test expects one token-signing call across the whole auth route,
but the baseline has two because it also renews host sessions. Reproduced against
the unmodified baseline; not silently removed or changed in this patch.

Before release: complete CI/full backend validation, verify provisioning against
a disposable PostgreSQL database, then provision and configure under controlled
deployment. Verify correct/wrong passwords, ordinary-host MFA, organization
isolation, disabled/expired exception and logout on the actual Host build.

This is NOT a complete Apple demo environment: fake property/reservation data,
Guest review access and hardware-review instructions remain to be prepared.
The current Demo Center is scoped to its existing internal property and must not
be reused by moving production data into this organization. No new mobile build
is generated by this backend change.
